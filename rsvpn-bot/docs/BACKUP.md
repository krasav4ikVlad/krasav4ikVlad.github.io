# Копии базы

Бот каждую ночь в 00:00 снимает копию всей базы, кладёт её на диск
сервера и присылает файл в личку админам. Ничего настраивать на сервере
не нужно: ни крона, ни `mongodump` — задача живёт внутри бота.

Снимок делает **отдельный процесс**, а не сам бот. Причина простая:
снимок большой базы ест память, а у бота она ограничена
(`max_memory_restart` в pm2) — процесс убивали на середине копии, он
поднимался, начинал заново, и так сотни раз без единой доведённой копии.
Теперь бот остаётся лёгким и только следит за ходом дела по файлу
состояния.

Из этого следует приятное: **перезапуск бота больше не обрывает копию**.
Обновление посреди ночного снимка — снимок живёт своей жизнью и допишет
файл, даже если бота в этот момент не станет. О результате бот узнает из
того же файла.

Снять копию руками можно и без бота:

```bash
cd /home/rsvpn-bot
.venv/bin/python -m scripts.dbbackup --force
```

Двух копий разом не бывает: пока идёт одна, второй запуск отменяется —
и по замку в процессе, и по недописанному файлу на диске (его видно и
после перезапуска бота). «Идёт» определяется не возрастом файла, а его
ростом: живой снимок дописывает пачку каждые несколько секунд. Если в
файл не писали пять минут, писать в него уже некому — он считается
обрывком, убирается, и снимок делается заново.

Прерванная копия (бота перезапустили, процесс убили) оставляет после
себя файл `.broken` и запись о прерванной попытке. Следующую бот начнёт
не раньше чем через полчаса, а после трёх обрывов подряд перестанет
пробовать до следующего срока и напишет, что смотреть на сервере. Это не
упрямство: круг «копия — смерть процесса — копия заново» не лечится
повтором, он лечится причиной. Чаще всего это `max_memory_restart`
в `ecosystem.config.js`.

Если бот всё же считает, что копия идёт, а вы уверены в обратном:
`/backup force` начнёт новую, не глядя ни на метку, ни на паузу. В `/backups` видно,
когда в недописанный файл писали в последний раз.

Ход дела видно: и ночная копия, и `/backup` показывают полоску с
процентом и строкой о том, что происходит прямо сейчас. Ночная копия
живёт одним сообщением в личке — приходит с «начинаю», обрастает
полоской и в конце становится отчётом.

## Где лежат

По умолчанию `~/rsvpn-backups` (то есть `/root/rsvpn-backups`, если бот
запущен от root). Каталог нарочно вне папки бота — обновление `./scripts/update.sh`
делает `git pull`, и копиям там не место.

Имя файла: `RS_2-2026-09-30-0412.jsonl.gz` — база, дата, время.

## Что внутри

Построчный JSON с сохранением типов Mongo (даты остаются датами,
`ObjectId` — `ObjectId`), сжатый gzip. Одна строка — один документ:

```json
{"c": "users", "d": {"_id": {"$oid": "..."}, "user_data": {...}}}
```

Каждый снимок сразу после записи прочитывается обратно и сверяется по
числу документов. Если не сошлось — файл удаляется, а в админ-чат уходит
сообщение, что копия **не** сделана. Архив, который не открывается, хуже
отсутствия архива: на него рассчитывают.

## Команды

| Команда | Что делает |
|---|---|
| `/backup` | снять копию сейчас и прислать файл в чат (если он меньше 50 МБ) |
| `/backups` | какие копии есть, когда делались, сколько весят |

В `/backups` видно и то, что копия давно не делалась, — если последняя
старше двойного срока, об этом сказано прямо там.

## Настройки

Админка → Настройки → **Резервные копии базы**:

* **Делать копии базы** — выключатель;
* **Во сколько делать** — час по времени бота, по умолчанию 0 (полночь);
* **Сколько хранить** — 14 штук, старые удаляются сами;
* **Каталог для копий** — пусто означает `~/rsvpn-backups`;
* **Присылать файл в личку админам** — включено. Адресаты — только те
  id, что стоят в `.env`: в снимке вся база, почты, платежи и переписка
  с поддержкой;
* **Не слать файлы больше** — 45 МБ на один файл. Telegram не принимает
  документы больше 50, поэтому снимок крупнее режется на части.

Срок считается от назначенного часа, а не от времени последнего запуска:
перезапустили бота днём — расписание не сдвинулось. Пропущенная из-за
простоя полночь не теряется: снимок сделается при первой возможности,
иначе сутки остались бы без копии и никто бы не узнал.

## Если файл пришёл частями

Большой снимок приходит несколькими файлами `…jsonl.gz.001`, `.002` и так
далее; к последнему приложена команда сборки. Сложить обратно:

```bash
cat RS_2-2026-09-30-0000.jsonl.gz.* > RS_2-2026-09-30-0000.jsonl.gz
```

Порядок задаётся именами, так что `*` разложит их правильно. Дальше это
обычный снимок — восстанавливается как описано ниже.

## Восстановление

Отдельным скриптом и нарочно не кнопкой: восстановление базы нажатием с
телефона — это способ однажды потерять вечер.

Сначала посмотреть, что внутри (базу не трогает):

```bash
cd /home/rsvpn-bot
.venv/bin/python -m scripts.dbrestore ~/rsvpn-backups/RS_2-2026-09-30-0412.jsonl.gz
```

Залить в тестовую базу и проверить на ней:

```bash
.venv/bin/python -m scripts.dbrestore ~/rsvpn-backups/файл.jsonl.gz --into RS_2_test --yes
```

Залить в боевую:

```bash
pm2 stop rsvpn-bot rsvpn-api
.venv/bin/python -m scripts.dbrestore ~/rsvpn-backups/файл.jsonl.gz --yes --drop
pm2 start rsvpn-bot rsvpn-api
```

Скрипт спросит имя базы для подтверждения — это последняя проверка того,
что команда набрана в том окне.

`--drop` очищает коллекции перед заливкой, то есть возвращает базу ровно
к состоянию снимка. Без него документы из снимка перезапишут текущие по
`_id`, а всё, чего в снимке нет, останется на месте — так восстанавливают
случайно удалённое, не теряя того, что появилось позже.

## Вторая копия — наружу

Копия на сервере бота спасает от испорченной базы и не спасает от потери
самого сервера. Поэтому снимок умеет уезжать в объектное хранилище —
любое S3-совместимое: Cloudflare R2, Backblaze B2, Selectel, Timeweb,
VK Cloud. Протокол у всех одинаковый, меняются только адрес и ключи.

В `.env` бота (пример для Cloudflare R2):

```bash
BACKUP_S3_ENDPOINT=https://<account_id>.r2.cloudflarestorage.com
BACKUP_S3_BUCKET=rsvpn-backups
BACKUP_S3_KEY=<Access Key ID>
BACKUP_S3_SECRET=<Secret Access Key>
BACKUP_S3_PREFIX=rsvpn          # необязательно, папка внутри бакета
BACKUP_S3_REGION=auto           # необязательно, для R2 именно auto
```

`<account_id>` — Account ID из панели Cloudflare; ключи делаются в
**R2 → Manage API tokens**, права — **Object Read & Write**, и только на
нужный бакет. Публичный доступ к бакету включать не надо: бот ходит по
ключам.

Проверить, что всё сошлось, можно сразу: **`/backupcheck`** кладёт в
хранилище пробный файл, читает его обратно и удаляет. Без этой проверки
про неверные ключи скажет только ночной снимок — через сутки и после
получаса работы.

Ключи живут в `.env`, а не в настройках: настройки видны на экране
админки и лежат в той самой базе, копию которой мы и делаем.

Переключатель — в админке, «Увозить копию в хранилище». Старые копии там
убираются так же, как на диске, по числу из «Сколько хранить».

Когда копия уехала в хранилище, в Telegram файл **не отправляется**: там
он целиком, а в Telegram полез бы девятью кусками по 45 МБ каждую ночь.
Если хранилище отказало — Telegram остаётся последней дорогой наружу, и
файл приходит частями, как раньше.

Неудачная отправка **не отменяет снимок**: файл уже на диске и уже
проверен — это копия. В отчёте будет строка, что наружу она не уехала и
почему.

## Чего копии не заменяют

Если хранилище не настроено, копия лежит на том же сервере, что и бот, и
пропадёт вместе с ним. Тогда раз в неделю имеет смысл забирать свежий
файл к себе:

```bash
scp root@сервер:/root/rsvpn-backups/$(ssh root@сервер 'ls -t /root/rsvpn-backups | head -1') .
```

Или просто сохранять файл, который бот присылает по `/backup`.
